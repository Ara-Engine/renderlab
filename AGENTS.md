Read `docs/brief.md` and `docs/project-handoff.md` before implementation. Read `docs/research/industry-rendering-costs.md` before selecting rendering algorithms or making comparative performance claims.

- This is an independent public-facing Rust renderer. Its own users and development experience drive the design; Ara integration is deferred.
- Keep dependencies and compilation boundaries deliberate. Measure shader edit-to-image, incremental Rust edit-to-running-viewer, and startup-to-image separately from frame time.
- Speed (Islam, 2026-11-06): finish the work first and check rarely. Don't gate every step. Run checks when a variant is ready to keep, and batch them into one run. Make checks fast: one process that loads the asset once and runs every configuration, hash comparisons instead of full readbacks, crops or fixtures before the full quarry, CPU replays of saved buffers, 8 repeats unless nondeterminism is suspected, and reuse of warm per-tree targets. Don't wait for quiet windows except for a final performance claim.
- Treat verification latency as development latency. Reject experiments with a short targeted reproducer and paired sample first. Reuse valid baseline evidence; reserve broader checks for retained changes and specific unresolved risks. Scale benchmark repetitions to observed variance and the claim, rather than running a fixed large campaign for every edit. Report implementation and verification time separately during optimization work.
- Establish a small working viewer and shader reload loop before expanding rendering features. Keep the last working pipeline on shader errors.
- Verify the complete image, including silhouettes, shadows, transparency and motion. Region-average lighting scores alone do not certify visual quality.
- Keep fast development builds distinct from optimized performance measurements. Record hardware, scene, resolution, quality, build identity and contention with timings.

- No quality reductions (Islam, 2026-11-05). Quality is judged on the final visible image, static and in motion, against a high-sample reference, e.g. path-traced, Cycles-like or Unreal's film/path-tracer quality. The minimum is Unreal's high-fidelity game rendering; the target is film-quality. Any technique may reach that output: temporal accumulation, caching, denoising, approximations. Lumen-style tricks are acceptable when the final image passes, including under motion, disocclusion and lighting changes. Avoid screen-space techniques for core lighting and shadows: their off-screen and disocclusion failures conflict with this bar. A mode whose final image is below the bar is never a default, and is never presented as meeting it. Clarified 2026-11-06: the shipping floor is Unreal's quality, matched or beaten on every measure. Film quality is the target we work toward over time. Don't block a fast path that beats Unreal just because it isn't film-exact yet.
- Win with and without hardware ray tracing (Islam, 2026-11-06). Hardware features must never limit quality. The non-RT path is first-class: it must meet the same film-quality gates and beat Unreal's non-RT configurations (VSM, Lumen software) on matched workloads. The ambition is non-RT quality rivalling other engines' RT output. Every quality gate and Unreal comparison is measured on both paths. A feature that exists only with RT is incomplete until its non-RT counterpart passes the same gates.
- Shading must stay programmable. Users will write their own shaders to give games completely different visual styles, as in other engines. Do not bake lighting-model-specific shortcuts into receiver data, hit records or dispatch structure in ways that would block user-authored material/shading stages. Record any such constraint when performance work introduces it.
