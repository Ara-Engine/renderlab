# Shader compile structure for P-PIPE

The first low-risk screen is dead-branch/dead-function cleanup before driver submission. Then split secondary traversal from programmable hit shading, reusing the existing primary-hit boundary. A larger WGSL file alone is not evidence for a split: wgpu already emits separate entry-point SPIR-V, and the expensive dependency is shared traversal, cache access and lighting services reachable from a changing user shader.

**Evidence labels.** All counts, byte sizes, percentages and deltas in this note's census, edit tables, function inventory and cleanup screen are **CPU measurements from this study**, unless explicitly labelled otherwise. Source constants, version numbers and command arguments describe configuration. Proposed savings and driver effects are **estimates**; there is no driver compile-time measurement here. The integration observations—NVIDIA non-RT exceeding the reported cold-start timeout, Radeon starting sooner and a new glass/program variant adding a long stall—are **reported in the repo**, not reproduced on this machine: [M8 integration findings](m7-gaps.md#m8-integration-findings-at-v013-ara-bridge-2026-11-10). The roughly sixfold driver improvement for optimizer-processed SPIR-V is likewise **reported**, not established by these CPU results ([P-PREVIEW lead](m7-gaps.md#L747)).

## What is actually composed and sent to Vulkan

The CPU seam is real; composition never needs a device. [program.rs:428](../src/program.rs#L428) concatenates visibility/ray head, common API, transmission, clustered-light services, decals, specular filtering, stage API, optional GI/reflection services, atmosphere, parameter declarations, the user program, and a generated entry. Hooks and token use decide whether GI, reflection and view-dependence code are added. [primary_ray_gpu.rs:48](../src/primary_ray_gpu.rs#L48) builds RT heads, [the non-RT counterpart](../src/primary_ray_gpu.rs#L66) supplies visibility stubs and software-reflection geometry, and [shading_heads](../src/primary_ray_gpu.rs#L204) finishes the material-facing heads. Primary visibility is already independent of user programs.

[Program compilation](../src/program_gpu.rs#L420) composes and validates all relevant modules, while pipeline sets are built for active variants; [streamed](../src/program_gpu.rs#L958) and [list](../src/program_gpu.rs#L998) pipelines have separate first-use paths. [GI cell shading](../src/gi_cache.rs#L903) embeds `surface`, `scatter` and `emission`; [glass composition](../src/transparency_gpu.rs#L78) embeds surface/shading/transmittance and a separate lobe entry. [Glass reflected-hit composition](../src/transparency_reflection.rs#L29) embeds another program-dependent traced module. Source inclusion does not imply all included functions survive backend entry processing.

Do not reuse the older whole-module emission heuristic in `reload_tests.rs` as a picture of this backend. The locked wgpu-hal source's [Vulkan adapter](https://github.com/gfx-rs/wgpu/blob/40f4a34ebaf56f9a046231f54125ad046239d3f3/wgpu-hal/src/vulkan/adapter.rs#L2297) enables separate entry points unconditionally; [compile_stage](https://github.com/gfx-rs/wgpu/blob/40f4a34ebaf56f9a046231f54125ad046239d3f3/wgpu-hal/src/vulkan/device.rs#L700) invokes `process_overrides` for the selected stage/entry, then `write_vec`. The tool does the same, rather than emitting every incidental prelude entry. Naga's [process_overrides fast path](https://github.com/gfx-rs/wgpu/blob/40f4a34ebaf56f9a046231f54125ad046239d3f3/naga/src/back/pipeline_constants.rs#L93) can skip compaction for a single entry without overrides; the tool preserves that behavior. Compaction is not general constant-control-flow elimination.

**Exact policy, declared hardware profile.** Engine modules default to unchecked runtime execution; arbitrary user modules remain checked ([pipeline_compilation.rs:136–207](../src/pipeline_compilation.rs#L136)). [program_gpu.rs:384](../src/program_gpu.rs#L384) treats the exact bundled standard program as trusted; edited standard/toon go through the checked API. GI-cell and glass reflected-hit creation currently use the engine-module API even though they compose user text; the catalogue records that actual call site, rather than inferring trust from the presence of user code. A custom prelude or environment override can also latch engine checks on; the default-policy comparison below assumes neither.

The tool mirrors [Vulkan adapter options](https://github.com/gfx-rs/wgpu/blob/40f4a34ebaf56f9a046231f54125ad046239d3f3/wgpu-hal/src/vulkan/adapter.rs#L2826) with this explicit **reference profile**:

| Setting | Checked | Unchecked |
|---|---|---|
| Naga parsing + validation | Enabled, all validation flags | Same |
| SPIR-V version | 1.6, Vulkan 1.3 profile | Same |
| Writer flags | LABEL_VARYINGS, FORCE_POINT_SIZE; DEBUG off | Same |
| Value/array indexing | Restrict | Unchecked |
| Buffer/image-load bounds | Unchecked using reference hardware robustness | Unchecked |
| Descriptor-array bounds | Unchecked, matching backend policy | Unchecked |
| Loop bounding, ray-query initialization tracking, integer division guards | Enabled | Disabled |
| Workgroup zero initialization | Native, enabled independently of checks | Same |
| Binding map | Explicit source binding numbers and fixed WGSL array sizes; fake bindings disabled | Same |
| f16 storage I/O | Disabled | Same |

`SHADER_STRUCTURE_ROBUST=0` selects shader buffer/image restrictions; `SHADER_STRUCTURE_NATIVE_ZERO=0` selects the polyfill, for adapter-profile follow-up. These switches are recorded in JSON. Mesh/task settings do not affect the catalogued stages. Validation capabilities are a structural superset, not a device-support certificate.

**What is not device-exact:** the real adapter supplies its capability allowlist, robustness and zero-init support, debug flags and pipeline-layout descriptor remapping. In particular, [wgpu-hal's bind-group layout code](https://github.com/gfx-rs/wgpu/blob/40f4a34ebaf56f9a046231f54125ad046239d3f3/wgpu-hal/src/vulkan/device.rs#L1408) assigns consecutive Vulkan binding numbers from layout entries; the tool uses identity descriptor numbers. Fixed array counts are taken from WGSL. Thus these are exact measurements of reproducible CPU binaries using the engine's entry-processing and check policies, **not SHA fingerprints of the RTX driver's actual input**. Numeric binding decorations by themselves do not alter encoded size, but actual layouts and adapter settings must be captured to certify an identical binary. There is no need to stop at WGSL composition; CPU emission and structural comparison are possible, while that last runtime fingerprint and driver work remain unavailable here.

## Results that decide the first cuts

The largest checked non-RT standard binary is `program-list-soft-streamed/primary_shade_list`: **232,912 bytes, 13,967 instructions, 192 functions, 44 loops, maximum intra-function nesting 4**, from **3,345 WGSL lines**. Unchecked: **220,404 bytes**, a reduction of **12,508 / 232,912 = 5.37%**. These are static counts, not executed work. The largest RT standard binary is `program-list-hard-streamed`: **216,236 checked bytes**, **202,652 unchecked bytes**.

For a closer hard/resident pair: non-RT **227,392** versus RT **211,080** checked bytes, or **(227,392 − 211,080) / 211,080 = 7.73%** larger. This modest byte difference does not explain the reported much larger NVIDIA latency by itself. The software path has deeper traversal and private stack indexing, while both shaders contain nested material, visibility and integration helper trees. Driver passes, inlining, scalarization and loop transforms are plausible explanations, **not measured causes**.

In that non-RT hard/resident checked binary, the largest body is `rl_local_shadow_map`: **19,240 bytes / 1,122 instructions**, with **6 loops / depth 3**, called from **1 static site**. `rs_trace` is **6,608 bytes / 431 instructions**, with **4 loops / depth 4**, called at **2 sites** (closest/any-hit wrappers). `gi_prepare` is **7,152 bytes**, `filtered_brdf` **7,688**, `decal_inputs` **6,376**. `spatial_brdf` has **9 static callers**, `brdf` **10**, and `rl_pcf_weight` **34**. Counted calls are potential driver inline sites, not a statement that every call is inlined or executed. Function bodies, callers and loop depth for every baseline binary are in the inventory below.

## The user-edit experiment

Inputs differ only in program text. `standard` is exact [standard.wgsl](../shaders/programs/standard.wgsl); `toon` is exact [toon.wgsl](../shaders/programs/toon.wgsl). `glass_tint` derives from standard by replacing just the transmittance return:

```diff
-return (1.0-s.alpha)*(1.0-fresnel)*s.base;
+return (1.0-s.alpha)*(1.0-fresnel)*s.base*vec3<f32>(0.8,1.0,0.6);
```

This is a controlled **glass user-program variant**, not new glass geometry, a changed uniform, or a switch from an opaque pipeline to a newly compiled glass family. The census already includes both families. A uniform-only material edit should not change these source binaries. Replacing standard with toon is also not an equal-quality optimization: it deliberately removes rendering features and changes style, useful here only to expose compiler dependencies.

The source-only glass edit changes just `transparency-glass/fs_transparent` on each path, by **+76 bytes each**; all other baseline binaries are byte-identical in each matched check mode. The opaque shader, GI cell shader and RT glass-reflected-hit binary do not change. The real default transition from exact standard to any user text also enables checks in program modules: **24 binaries change**, even though only **2** changed from the glass logic. The tables separate these effects.

A changed SHA at equal length is still a change; an unchanged SHA is not a guarantee of a driver cache hit. [ModuleCache](../src/program_gpu.rs#L28) is keyed by the full composed WGSL, so an unused-hook edit can invalidate its front-end cache even if entry-point SPIR-V stays identical. Driver keys also include layout, state, flags and cache state. Conversely, “the source is embedded everywhere” does not mean all those entry-point binaries change. Record the active pipeline families in P-PIPE, especially the first use of a glass/list/streamed variant.

## Where to cut, in implementation order

Putting helper text in another `.wgsl` file does not create a driver compilation boundary. These compute pipelines have no ordinary cross-module WGSL function linkage. The existing [Vulkan graphics-library policies](../src/program_vulkan.rs#L18) separate graphics subsets; their comments explicitly leave compute monolithic. A durable compute boundary needs a dispatch and an explicit record/queue, or an independently demonstrated backend linking facility. A no-inline hint may reduce optimizer work but still resubmits the module.

| Rank / action | What can remain independent of program edits | Boundary data and programmability contract | Benefit / tradeoff / first rejection gate |
|---|---|---|---|
| First: early semantic cleanup and accurate cache keys | Constant-dead helper trees, plus already separate geometry/visibility/temporal modules | Preserve all bindings, entry ABI and runtime checks. Prune by validated constant control flow, not material names or textual guesses. Key emitted code with specialization/check profile/layout; persist successful driver cache batches so killed cold starts keep progress. | **Measured** cleanup saves 15–17% in the screened hard/resident pairs, without inlining. **Estimate:** driver savings unknown; begin with the existing optimizer interception and validate target output. Compare cold same-state pipeline creation with raw/cleanup/broad `-O`, then a cached revert; reject if no latency win or any changed shader result. This study does not implement cleanup or cache persistence. |
| Second: secondary ray generation → shared traversal → per-hit program → receiver resolve | The non-RT BVH walker or RT query kernel, and geometric hit reconstruction, should not contain `surface`/`shade` | A ray task needs origin/direction, range, query kind, source receiver/sample identity, lobe weight/PDF and footprint/cone. A hit needs instance/placement and primitive identity, barycentrics/distance, validity/front-side, destination program/material identity, parameter revision/offset, texture bindings and ray differentials. Misses carry environment direction/footprint, not a BRDF result. Queue/bin hits by the **hit's** program, run its surface/shading services, return radiance/sample identity to the receiver. | **Measured structural lead:** `rs_trace` alone occupies 6,608 bytes and has depth 4 with 2 call sites in the hard/resident binary. **Estimate:** that traversal body and its support are candidates to move out of each edited shader, but net bytes and driver time require re-emission; extra dispatches, queue bandwidth, divergence and live state can erase the runtime gain. Reject a CPU prototype if traversal still appears in program SPIR-V, hit identity is lost, or per-program state cannot be preserved. Then measure first-use/edit latency and steady frame cost on both paths. |
| Third: shared receiver-service kernels, starting with GI lookup and local shadow visibility | Cache hashing/decode/interpolation, clustered-light incidence and map/trace visibility for a declared receiver/query | Pass geometric receiver data, exact normals/footprints, light/query IDs, cache revision and returned visibility/transmission. GI outputs should retain directional radiance/SH/lobe data and validity, not preapply a metallic-roughness diffuse/specular response. A shader may choose its own light loop, BRDF, surface normal, stylized bands and environment integration. The second boundary is worth prototyping even if there are no shader edits: it isolates the deepest software traversal from the large material/light helper graph, makes compile profiling attributable, and gives the engine a place to implement correct mixed-program reflected-hit shading. It is **not proven faster** during rendering. Keep it only if the whole image and measured development/frame costs justify it. Fixed `virtual-shadow-virtual/vsm_lookup` is also large (**99,192 checked bytes**) and worth separate compile-label profiling, but it is already program-independent; splitting it again will not reduce the code changed by a user edit. Primary trace, VSM/S4, GI tracing/gather/filter, TR1, atmosphere and post stay outside the user-program rebuild set.

### State that a wavefront sketch must not hide

The engine allows a user-defined `Surface` and program-private globals: [analyse](../src/program.rs#L707) prohibits user bindings, not private state or a different surface layout. Calling `surface` again after tracing is not automatically equivalent to continuing the original invocation. Either keep dependent surface/shade work together, generate per-program continuation/state packing, or establish a compatible execution contract with an explicit fallback for existing programs. Do not impose purity as an undocumented optimization. Re-entrant hit shading must also preserve the receiver's parameters and private service state; today [reflection code](../shaders/reflections.wgsl#L195) changes parameter selection for the hit and restores the receiver afterward.

The baseline itself has an open contract defect: reflected hits use receiver-program code with the hit material, and foreign-program parameter fallbacks exist ([M8 gap](m7-gaps.md#m8-integration-findings-at-v013-ara-bridge-2026-11-10), [glass source](../src/transparency_reflection.rs#L35)). “Preserve today's bytes” cannot certify correct hit programmability. A new hit queue must carry program identity and dispatch the hit's own shader/parameters; neither a fixed PBR material record nor silently using the first program is an acceptable boundary. This is exactly why generic radiance/visibility and hit records belong at the seam, while the user's lighting response remains code.

A helper-library/no-inline screen can precede new queues, but inspect actual SPIR-V names and flags: the [preview selection code](../src/program_vulkan.rs#L557) uses `OpName`, while this census's shipping-style binaries have DEBUG off. Its fallback can mark all non-entry functions, so a “selected helpers” experiment is not proof that only the named helpers changed. This tool obtains names from a separate debug emission and verifies ordering/opcode correspondence without measuring debug binaries.

## Optimizer result and validity limit

`spirv-opt -O --target-env=vulkan1.3` ran serially, with identical-input hashes cached across variants. Across the measured records, **494 pass strict optimization; 680 fail strict validation**, representing **121 passing and 266 failing distinct input hashes**. All failures report **VUID-StandaloneSpirv-None-10684**, explicit ArrayStride/Offset layout on Private, Function or Workgroup types. For example, the non-RT material shader's private SH array is rejected. This is a concrete compatibility discrepancy between these Naga outputs and this validator/profile, not a measured GPU/device rejection. The tool preserves the error, then runs `-O --skip-validation` as a separate size-only diagnostic; that diagnostic completed for all failing inputs. **Do not send those diagnostic outputs to the driver as a validated shipping change.** Reconcile the validator/backend/profile discrepancy and verify target semantics first.

Every baseline row below has a strict `-O` size where available; `†` identifies the skip-validation result instead. It would be misleading to omit the failed cases or call the complete optimizer run valid. Baseline alone has **230 failing records** across the two check modes.

Broad `-O` often expands this corpus: non-RT hard/resident checked **227,392 → 1,825,068 bytes**, or **8.03×**, and the largest checked non-RT list/streamed shader **232,912 → 2,058,256**, or **8.84×** (both unvalidated diagnostics).
