## Matched content and limits

Both adapters consume the **same prepared RLA**, material factors, transforms, right-handed Y-up metre coordinates, sun direction/lux, local-light units, fixed manual exposure, dimensions and camera replay. Renderlab and Ara native raster/hybrid consume the shared mip bytes. The public legacy fidelity API accepts only mip zero and generates its own mip chain: that texture-filtering difference must remain recorded in fidelity rows. No scene import happens during timed frame segments. Ara native raster/hybrid preserves source instances. The public fidelity adapter flattens them; that is recorded and its startup/memory cannot be relabelled as the native instanced path. RLA vertex colours other than white and unsupported moment/variance normal encodings fail explicitly.

The controlled displayed curve is Narkowicz ACES-fit + sRGB: Ara `AcesFit`, Renderlab `Tonemapper::Filmic` (the matching formula). Bloom, lens blur, vignette and participating media are disabled **for this explicitly named subset**. Full shipping-feature rows retain their defaults and must not borrow the subset's speed result. The sun radius is 0.00465 rad on both engines because Ara main fidelity fixes it internally; original `game_scene` uses 0.04. Both cameras use a 0.1 m near plane; Ara has infinite reversed-Z, Renderlab uses a 10 km far plane with matching perspective rays. Normal comparison adapters use 16× material anisotropy on this GPU and reject unsupported sampler substitutions. The completed initial untextured smoke preceded the explicit 16× override and persistent program-cache setting; its exact executable hash remains in its process record.

Outputs:

- `engine.json`: actual path/settings/adapter, per-frame CPU service or submission costs, GPU stage timestamps where public, startup-to-first-image readback. - `process.json`: scene and asset hashes, binary hash, source SHA and tracked status, harness hashes, hardware/driver/UUID, resolution, build profile, contention declaration, lease/order, process wall time, fresh-ready-file latency, resource samples and image hashes.

- `startup-memory.json`: process-specific Windows `GetProcessMemoryInfo` working set, cumulative peak working set, private commit and peak pagefile bytes. This small snapshot is atomically persisted every 200 ms until first readback, so a guard termination preserves the last observed bound. It excludes driver allocations in other processes and guard/interpreter memory. The first attempts predated this recorder; their engine startup working-set peaks are **unavailable**, not inferred from system free memory.
