# M6 CPU shadow planning

This bounded unit implements private shadow-view math and caster assignment in `src/shadow_plan.rs`. It is not an integrated shadow renderer or M6 acceptance. It follows the selected forward-HDR/conventional-depth contract in [m5-lighting-plan.md](m5-lighting-plan.md); it adds no second lighting API, GPU resources, shaders, scheduling, caching, or virtual cut.

## Inputs and outputs

`directional(&Camera, viewport, travel, split_ends, resolution, bounds)` produces one view per supplied interval. The first starts at `Camera::near()`. Split ends must be finite and strictly increasing. The last end is the requested shadow distance. It can exceed the camera far plane conservatively: the current Camera exposes near and FOV, but no far accessor. The adapter should choose a useful distance explicitly; this module never reconstructs an unreliable far distance from rounded projection coefficients. Four intervals are a possible caller policy, not a limit or a hidden default. A test exercises 65 intervals. Directional resolution must be at least two, because nearest-texel snapping needs space for its half-texel displacement; perspective views accept any nonzero resolution. Device texture limits belong to the later adapter.

`spot(position, travel, outer_half_angle, LocalRange, resolution, bounds)` produces one square perspective view containing the circular cone. The half angle must be strictly between zero and pi/2. M5 permits a pi/2 spot; a shadow request for that case needs an explicit adapter decision (reject it or provide another representation), never a silently narrowed cone.

`point(position, LocalRange, resolution, bounds)` produces six views in +X, -X, +Y, -Y, +Z, -Z order. Face orientation is conveyed by each matrix; this is not an implicit texture-cube UV convention. A later sampler must use these matrices or explicitly reconcile its face orientation and texture-Y mapping.

`LocalRange` is radial shadow coverage, independent of M5's optional photometric attenuation range. It requires finite `0 < near < far`. For spots the axial near plane is `near * cos(outer)`; for points it is `near / sqrt(3)`. This includes cone-rim and cube-corner points at the requested radial near distance. Axial far is the radial far distance, so perspective corners include unnecessary space beyond that sphere. A light with unlimited photometric range still needs a finite shadow coverage decision. **Casters inside the excluded near region are not guaranteed to render, even if they block a more distant receiver.** Root must choose/check that domain against actual source geometry, or add a separately verified near-plane strategy. The lighting distance regularization does not establish an empty caster region.

`Bounds` is a private finite, ordered world AABB per full submitted caster, in caller order. Zero-volume bounds are valid. Input errors return `Error::InvalidInput` without publishing a partial result. All directions are normalized in f64, accepting finite nonzero vectors even when f32 length arithmetic would overflow/underflow. Nonfinite, singular, or subnormal output matrices and unrepresentable depth/texel intervals are rejected. This is a numerical domain, not a device/resource budget.

Each `ShadowView` owns its RH world-to-view, view-to-clip and authoritative world-to-clip matrices, resolution, actual axial depth interval, view kind, optional orthographic world-units-per-texel, and caster indices. Forward is -Z; depth is ordinary near=0, far=1. The combined matrix is formed in f64 before conversion to f32; upload it directly rather than recomputing the product in f32. The module owns no geometry and never changes source positions, indices or transforms. Empty scenes and no-hit views retain finite matrices with an empty caster list; the GPU adapter can clear those maps to depth 1.

## Directional conservatism and stability

Each receiver slice is enclosed by a sphere centered halfway along its camera-forward depth interval. Its radius uses the far-plane diagonal and half the slice depth; that encloses both endpoint planes. A square encloses the sphere in light XY. This intentionally spends some resolution to avoid a tightly fitted rectangle changing scale as the camera rotates. It does not claim the smallest sphere or optimal cascade distribution.

The square center is snapped to a world-anchored texel grid. Its half width includes the maximum half-texel snap displacement and a coordinate-roundoff guard. The guard is 16 f32 epsilons times the next power-of-two coordinate magnitude; it is constant within a magnitude bin. With fixed FOV, aspect, split distances, light direction and precision bin, small translations preserve XY until a grid boundary is crossed, and camera rotation preserves the extent. Crossing a precision bin changes the guard. Changing the light direction changes the basis; the least-aligned helper axis can switch, so this is not a promise of smooth moving-sun roll or GPU image stability.

All submitted bounds are transformed into the light basis once per directional light. A cascade includes bounds whose projected XY overlaps its square and whose maximum light-space Z is not entirely behind the receivers. +Z is lightward because M5 `travel` points away from the source. There is **no camera visibility or camera distance restriction on caster lookup**. An offscreen blocker arbitrarily far toward the source can extend the depth range.

Z includes every receiver corner and the full Z extent of each assigned AABB, with a rounding margin and a minimum 1 mm margin. Extending both ends for the full assigned bounds is conservative and can waste depth precision. XY remains receiver-fitted: portions of an assigned object outside that square are intentionally clipped because parallel light rays from there cannot reach that receiver footprint. It is not a claim that every corner of every partially overlapping caster fits in XY. A huge or loose AABB can cause excess work. No scene-tight optimization is claimed.

Local caster assignment rejects a box only when its support is outside one homogeneous clip plane. This includes crossing boxes and boxes enclosing a light/frustum; it can retain boxes that do not actually intersect the circular cone or radial domain. Rounding tolerance uses the original matrix-row magnitudes before far-plane subtraction, avoiding an underestimated tolerance when those rows nearly cancel.

CPU tests exercise actual f32 matrix multiplication with a 3e-5 normalized-clip tolerance, plus separate conservative-assignment checks. F64 fitting and the directional margins help translated scenes; they do not restore detail already lost in f32 source coordinates or prove arbitrary large-coordinate GPU precision. The translated coverage test uses an origin up to 2,000,000 metres, a 40 m directional receiver interval and an offscreen caster 2,000 m lightward. The local coverage case there uses a 32..4096 m domain. A separate cancellation test checks caster retention, not precise clipping of a centimetre-scale local view at that origin.

## Exact integration seam for root

1. After M5-A acceptance, adapt the existing `Light` variants to these private functions. Pass the same away-from-source `travel`. Add shadow coverage/resolution policy at that boundary; this module has no duplicate public `Light` or IDs. The temporary module-local dead-code allowance can go once used.
2. Build world AABBs from **all submitted slots and transforms**, with conservative affine-bound conversion, before camera-visible-ID filtering. Keep a caller-owned mapping from bounds index to original draw/slot. For virtual geometry use the complete published legal cut, not just camera-visible pages. Do not infer tighter source bounds from a simplified visible fragment.
3. On an admitted frame, assign every planned cascade/spot/point face a **disjoint aligned uniform range or distinct buffer/bind group**. Write all required matrices before the common submission. Rewriting one shared range for several passes would make every pass use the last matrix. Apply the existing in-flight resource ownership and admission rules; a busy frame cannot pair new transforms with old maps.
4. Render unchanged source geometry/position/sidedness with each view's `world_to_clip`, and look up its depth with the same matrix. Depth textures, comparison sampling, texture-Y conversion, filter footprints, bias, transitions and resource accounting remain GPU-adapter work. Current geometric padding is **not a PCF filter guard band**. Cascade transition bands need overlapping receiver coverage before blending; point-face filter seams need an explicit sampling solution.
5. First maps redraw every admitted lit frame. No cache is present. Shadow-view detail demand must ultimately max-merge with camera normalized error into **one legal virtual cut** before M6 acceptance. A separate per-light/per-placement cut is not introduced here. Compare offscreen/thin/grazing casters against full source geometry and retain existing page-use stamping after shared submit.

## Work and memory implications

CPU fitting scans N submitted AABBs and each of C cascade footprints: O(N + C*N) work, O(N) transformed-bound scratch and up to O(C*N) owned caster indices. A spot scans N bounds; a point light scans them for each of six faces. Empty lists still produce views. No broad-phase, persistent scratch cache or scheduler is added without measured need.

For later single-sample 32-bit depth storage, unpadded base-map bytes are `4 * sum(resolution^2)` over views: for equal resolution R, C cascades cost `4*C*R^2`, one spot `4*R^2`, and one point `24*R^2`. This excludes alignment, retained in-flight generations, uniforms, atlas padding and filtering resources. Geometry can be redrawn in several overlapping views; simultaneous demands can refine the shared virtual cut further. No GPU cost, quality advantage, Unreal parity or performance superiority has been measured for this unit.
